1. Genel Bakış

Switchly daha önce yalnızca Boolean flag desteklemiyordu — bir feature açık/kapalı. Bu çalışmada Multivariant (çoklu varyant, A/B test, kademeli rollout) desteğini uçtan uca ekledik: schema, create flow, weight yönetimi, evaluate, SDK ve variant CRUD.

Phase 1
Schema + Migration
2 yeni weight tablosu, navigation property'ler, EF Core migration
Phase 2
CreateFlag + Variants
CreateFlag artık Variants array kabul ediyor; Multivariant için min 2 zorunlu
Phase 3
Weight Yönetimi
Env-level ve targeting-level variant ağırlıklarını set eden 2 endpoint
Phase 4
Evaluate + SDK
EvaluateFlag variant döner; SDK GetVariant API; deterministik bucket
Phase 5
Variant CRUD
Add/Update/Delete endpoint'leri — UI variant yönetimi için

2. Neden Multivariant?

İki temel use case ayrımı:

SenaryoDoğru tipNeden
Yeni feature (öncesi yok) Boolean Açık/kapalı yeterli; kademeli rollout (RolloutPercentage) ile kontrol edilir, sorun çıkarsa kapatılır.
Var olanı değiştiriyorsun (eskisi ile karşılaştırma) Multivariant Kontrol grubu zorunlu. Boolean'da kullanıcıya "yeni mi eski mi gördü" etiketi yok → analytics segmentlemesi mümkün değil. Multivariant'ta her kullanıcıya variant_key atanır, conversion / error rate karşılaştırılır.
Aynı anda 3+ alternatif Multivariant Algoritma karşılaştırması (algo_v1 / algo_v2 / algo_v3). İki Boolean flag mantıksal olarak yetersiz — kullanıcı her ikisine de düşebilir.
CI/CD kill-switch senaryosu: 2 variant ile yayına aldığın feature (örn. treatment) prod'da hata almaya başlarsa, tek PUT ile treatment: 0, control: 100 set ederek anında geri dön. Ağırlık tabloları bu kullanım için optimize edildi.

Request/Response Şablonları

CreateFlag — Multivariant örneği

POST /api/flag/create
{
  "organizationId": "...",
  "projectId": "...",
  "key": "checkout_redesign",
  "name": "Checkout Redesign A/B",
  "type": 2,                          // 1=Boolean, 2=Multivariant, 3=Config

Yan etkiler:

  • Tüm env'ler için FeatureFlagEnvironment fan-out yaratılır.
  • Default env'e baseline weight: ilk variant=100, diğerleri=0 (Boolean'daki "default env=AllUsers/100" karşılığı).
  • Diğer env'lere weight set edilmez — kullanıcı /variant-weights ile belirler.

Set Env Variant Weights

PUT /api/flag/environment/{flagEnvironmentId}/variant-weights
{
  "weights": [
    { "variantId": "...", "weight": 50 },
    { "variantId": "...", "weight": 50 }
  ]
}

Validation: Liste boş değil, weight ∈ [0,100], variant ID'ler benzersiz ve bu flag'e ait, toplam=100, sadece Multivariant flag.

6. Variant Bucket Algoritması

Server-side ve SDK-side eval'in aynı kullanıcıya aynı variant'ı atadığından emin olmak için deterministik bir hash fonksiyonu kullanılır:

bucket = SHA256("{flagKey}:{userKey}").firstUInt32() % 100   // 0..99

Variant'lar SortOrder'a göre sıralı, cumulative weight hesaplanır:

cumulative = 0
foreach variant in flag.variants ordered by SortOrder:
    w = weights[variant.Id]
    if w <= 0: continue
    cumulative += w
    if bucket < cumulative:
        return variant
return Off

Örnek

VariantWeightCumulativeBucket aralığı
control30300–29
treatment_a508030–79
treatment_b2010080–99
userKey yoksa: Multivariant flag'de userKey null veya boş ise stable bucket hesaplanamaz → safe-default Off döner (isEnabled=false, variantKey=null). SDK ve server bu konuda hizalı.
Determinizm garantisi: Aynı (flagKey, userKey) → aynı bucket → aynı variant, hem server hem SDK tarafında. SortOrder'ın stable olması bu yüzden önemli (Reorder operasyonu bilinçli olarak MVP dışı bırakıldı).

8. E2E Örnek: A/B Test + Kill Switch

1. Flag oluştur

POST /api/flag/create
{
  "organizationId": "$ORG", "projectId": "$PROJ",
  "key": "new_recommendations", "name": "New Recommendations",
  "type": 2,
  "variants": [
    { "key": "control",   "name": "Eski algoritma" },
    { "key": "treatment", "name": "Yeni algoritma", "payloadJson": "{\"model\":\"v2\"}" }
  ]
}
→ { "data": { "id": "$FLAG_ID" } }

2. Prod env'de 50/50 A/B test başlat

PUT /api/flag/environment/$PROD_FLAG_ENV_ID/variant-weights
{ "weights": [
    { "variantId": "$CONTROL_ID",   "weight": 50 },
    { "variantId": "$TREATMENT_ID", "weight": 50 }
]}

3. Backend / SDK eval

// Server-side
POST /api/flag/evaluate
{ ..., "userKey": "user-42" }
→ { isEnabled: true, variantKey: "treatment", variantPayloadJson: "{\"model\":\"v2\"}" }

// SDK
var result = client.GetVariant("new_recommendations", userKey: "user-42");
// result.IsOn == true, result.VariantKey == "treatment"

4. Kill switch — treatment hata alıyor, control'a kaç

PUT /api/flag/environment/$PROD_FLAG_ENV_ID/variant-weights
{ "weights": [
    { "variantId": "$CONTROL_ID",   "weight": 100 },
    { "variantId": "$TREATMENT_ID", "weight": 0 }
]}

Bir sonraki eval'de (server-side anında, SDK pull interval kadar gecikmeli) tüm kullanıcılar control'a döner. Treatment variant silinmez — incident sonrası tekrar açmak için weight'i artırmak yeterli.

10. Tasarım Kararları

Neden iki ayrı weight tablosu (env + targeting)?

Tek polimorfik tablo (OwnerType, OwnerId, VariantId, Weight) yerine iki ayrı tablo tercih edildi:

  • EF'de referential integrity (cascade delete) daha temiz
  • Index'ler daha selective
  • Query/projection'lar daha okunabilir
  • Polimorfik tablonun esneklik avantajı bu domain'de işe yaramıyor

Neden Boolean'ı 2 implicit variant'a (on/off) çevirmedik?

Unified design (LaunchDarkly tarzı) teorik olarak daha temiz olurdu — ama:

  • Mevcut Boolean davranışını ve SDK API'sini kırardı
  • Migration'da on/off variant'ları geriye dönük yaratmak gerekirdi
  • MVP hızını öldürürdü

Pragmatik Yol A (paralel) seçildi: Boolean dokunulmadı, Multivariant ayrı kod yoluyla işliyor. Evaluator'da tek bir if (Type == Multivariant) branch'i ile ayrım yapılıyor. Sonradan unify edilebilir.

Neden Variant.Key güncellenmiyor?

Analytics, log ve event sistemleri variant key'i stable identifier olarak kullanır. Runtime'da rename, geçmiş analitik verisini kirletir. Rename istenirse: yeni variant ekle, weight'leri kaydır, eski variant'ı sil.

Neden Reorder yok?

SortOrder bucket cumulative hesabını etkiler. Reorder etmek, aynı kullanıcının farklı bir variant'a düşmesine sebep olur — A/B test sonuçlarını sapıtır. MVP'de gerçek bir kullanım yoksa bu riski almıyoruz. UI yine de SortOrder'a saygı duyar.

Variant silinince weight'ler ne olur?

  • FK cascade ile ilgili weight kayıtları otomatik düşer
  • Env/targeting'in weight toplamı 100'ün altına iner (invariant geçici olarak bozulur)
  • Evaluator graceful: missing variant 0 weight gibi davranır, bucket o kullanıcıyı bir sonraki variant'a yönlendirir; hiçbiri uymazsa Off döner
  • Kullanıcı kalan variant'lar için weight'leri yeniden set etmeli

Neden auto-redistribute yok?

Variant silindiğinde kalan weight'leri otomatik dağıtmak (örn. treatment %50 silindi → control'u %100 yap) cazip gelebilir ama magic davranış. Açık API çağrısı (PUT weights) ile kullanıcının niyetini almak daha güvenli.
