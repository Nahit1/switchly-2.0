Büyük Resim

Backend bir Carter + MediatR vertical slice uygulaması. Her use case bir klasör, klasör içinde 2 dosya: bir Endpoint (HTTP route), bir Handler (iş mantığı). Hiçbir manuel registration yok — Carter ve MediatR runtime'da assembly tarar.

Multivariant için 4 ana akış var:

YAZ akışları (write)
CreateFlag (+variants) · Add/Update/Delete Variant · SetEnv/Targeting Weights
OKU akışları (read)
GetByProject (UI listele) · GetRuleset (SDK pull) · EvaluateFlag (direkt eval)
HTTP request ↓ Carter (Endpoint.cs) ─ route + body parse ↓ MediatR (Handler.cs) ─ auth check → validation → DB ops → response ↓ SwitchlyDbContext ─ EF Core 9 → PostgreSQL ↓ Response<T> envelope
Neden vertical slice? Her use case kendi içinde kapanır — command record, validator, response DTO, handler hepsi tek dosyada. Yeni use case eklemek = yeni klasör. Cross-cutting kaygı yok, refactor riski düşük.

1. Schema Katmanı

Multivariant için sadece 2 yeni tablo ekledik. Mevcut Variant tablosu zaten flag'e bağlıydı; eksik olan "hangi variant'a kaç % trafik" bilgisiydi — bunu env ve targeting seviyelerinde tutmamız gerekti.

Yeni entity'ler

FeatureFlagEnvironmentVariantWeight YENİ

Entities/FeatureFlagEnvironmentVariantWeight.cs

public class FeatureFlagEnvironmentVariantWeight
{
    public Guid Id { get; set; }
    public Guid FeatureFlagEnvironmentId { get; set; }
    public FeatureFlagEnvironment FeatureFlagEnvironment { get; set; } = default!;
    public Guid VariantId { get; set; }
    public Variant Variant { get; set; } = default!;
    public int Weight { get; set; }   // 0–100; toplam=100 app-side validate
}
Neden bu tablo? Bir flag'in FeatureFlagEnvironment'ında "hiçbir segment eşleşmediğinde default dağılım ne olsun?" sorusunun cevabı. Variant kendisi flag-level (her env'de aynı isimler), ama her env'in kendi default dağılımı olabilir.

FeatureFlagSegmentTargetingVariantWeight YENİ

Entities/FeatureFlagSegmentTargetingVariantWeight.cs

Yapısal olarak yukarıdakiyle birebir aynı — parent FeatureFlagSegmentTargeting. "Bu segment eşleşirse şu dağılımı uygula" bilgisini taşıyor, env default'unu override ediyor.

Neden iki ayrı tablo, tek polimorfik değil? Tek WeightOwner(Type, OwnerId, …) tablosu da yapılabilirdi ama EF'de cascade delete ve referential integrity polimorfik FK ile temiz değil. İki tabloyla: explicit FK, otomatik cascade, daha selective index, daha okunur projection. Domain'de polimorfizmin esneklik faydası yok.

Mevcut entity'lerdeki nav property eklemeleri DEĞİŞTİ

  • Entities/FeatureFlagEnvironment.cs → VariantWeights collection (env'in dağılımına ulaşmak için)
  • Entities/FeatureFlagSegmentTargeting.cs → VariantWeights collection
  • Entities/Variant.cs → ters yöne EnvironmentWeights + TargetingWeights (variant silinince ne düşeceğini EF'in görmesi için)

EF Configurations

Her tablonun kendi config dosyası (Context/Configurations/): cascade delete kuralları + composite unique index.

// FeatureFlagEnvironmentVariantWeightConfiguration.cs
builder.HasIndex(x => new { x.FeatureFlagEnvironmentId, x.VariantId })
    .IsUnique();

builder.HasOne(x => x.FeatureFlagEnvironment)
    .WithMany(fe => fe.VariantWeights)
    .HasForeignKey(x => x.FeatureFlagEnvironmentId)
    .OnDelete(DeleteBehavior.Cascade);

builder.HasOne(x => x.Variant)
    .WithMany(v => v.EnvironmentWeights)
    .HasForeignKey(x => x.VariantId)
    .OnDelete(DeleteBehavior.Cascade);
Neden cascade her iki yönde de?
  • Env silinince → o env'in weight kayıtları anlamsız, otomatik düşmeli
  • Variant silinince → onunla ilgili weight satırları da düşmeli; ama bu env'in toplam=100 invariant'ını bozar — evaluator buna toleranslı (missing variant'ı 0 weight gibi davranır)
Unique index neden composite? (EnvId, VariantId) aynı çiftin iki kez tanımlanmasını engeller — uygulama hatasını DB seviyesinde yakalar. Tek başına VariantId unique olamaz çünkü aynı variant farklı env'lerde weight taşır.

2. Flag + Variants Yaratma

Features/Flags/CreateFlag/CreateFlagCommandHandler.cs

Features/Flags/CreateFlag/CreateFlagEndpoint.cs

Ne yapıyor?

  • POST /api/flag/create → flag oluşturur + (Multivariant ise) variants'ı atomik şekilde yazar
  • Tüm env'ler için FeatureFlagEnvironment fan-out (eskisi gibi)
  • Multivariant'ta default env'e baseline weight yazar: ilk variant=100, diğerleri=0

Validation tablosu

Flag tipiVariants kontrol
Boolean (1)Variants gönderilemez → "Boolean flag için Variants gönderilemez."
Multivariant (2)Min 2 zorunlu; key non-empty; case-insensitive unique
Config (3)MVP'de zorunluluk yok (ileride payload zorunlu eklenebilir)

Default env'e baseline weight neden?

Boolean flag'lerde default env AllUsers/100 ile yaratılıyordu (flag baştan herkese açık). Multivariant'ta analoğu: ilk variant'a %100. Yoksa flag yaratıldığı anda evaluate edilirse weight yok → Off dönerdi. Predictable bir starting state için bu seed kritik.

Akış

handler.Handle() ├─ OrganizationMember check (auth) ├─ Project var mı + ait mi (defense in depth) ├─ Flag.Key benzersiz mi (project scope) ├─ ValidateVariants(type, list) (type'a göre kural) ├─ Insert FeatureFlag ├─ Insert Variants (varsa, SortOrder=index) ├─ Insert FeatureFlagEnvironments (env başına 1) ├─ Multivariant + default env → Insert baseline weights └─ SaveChanges atomik
Tek SaveChangesAsync neden? Hepsi tek transaction'da yazılsın diye. Yarısı yazılır yarısı yazılmazsa ortada zombie flag kalır.

Replace-all semantik

Endpoint mevcut weight kayıtlarını siler ve yenisini yazar. Partial update yok.

var existing = await context.FeatureFlagEnvironmentVariantWeights
    .Where(w => w.FeatureFlagEnvironmentId == env.Id)
    .ToListAsync(ct);

if (existing.Count > 0)
    context.FeatureFlagEnvironmentVariantWeights.RemoveRange(existing);

context.FeatureFlagEnvironmentVariantWeights.AddRange(fresh);
await context.SaveChangesAsync(ct);
Replace-all neden tercih edildi?
  • Toplam=100 invariant'ını korumak kolay (tek bir snapshot'ı validate ediyoruz)
  • API tüketicisi "tam state" gönderiyor → idempotent
  • UI tarafı zaten tüm satırları gösterip toplu kaydediyor — partial update mantıksız
  • Kill-switch senaryosunda {control:100, treatment:0} tek PUT yeterli

Validation chain

1. Owner var mı (env / targeting)                  → "bulunamadı"
2. User bu org'un member'ı mı                       → 401
3. Flag.Type == Multivariant mi                     → "sadece Multivariant"
4. Weight list non-empty                            → "boş olamaz"
5. Her weight 0–100 arasında                        → "0–100 olmalı"
6. VariantId'ler benzersiz                          → "aynı variant tekrar"
7. Tüm VariantId'ler bu flag'e ait                  → "flag'e ait değil"
8. Sum(weights) == 100                              → "toplam 100 olmalı"
Neden toplam 100? Bucket algoritması cumulative weight üzerinden çalışır (0..99 bucket'a maple). Toplam 100 değilse bazı bucket'lar boşa düşer ve Off döner — istenmeyen davranış. App-side enforce, DB'de constraint değil (PostgreSQL CHECK constraint eklenebilir ama esneklik kaybı).

5. Evaluate — Server-side

Features/Flags/EvaluateFlag/EvaluateFlagHandler.cs

POST /api/flag/evaluate — public, auth gerekmez. SDK kullanmayan istemciler için. Direkt server-side eval yapar.

Request & response

// Request
{
  "publicKey": "...", "projectKey": "...", "environmentKey": "...",
  "flagKey": "...", "userKey": "ali_123",
  "traits": { "country": "TR", "plan": "premium" }
}

// Response
{
  "isEnabled": true,
  "variantKey": "treatment",
  "variantPayloadJson": "{\"color\":\"#10b981\"}"
}

Tek-query snapshot pattern

Önceki versiyonda 5 ayrı query vardı (org → project → env → flag → flagEnv). Yeni versiyonda tek projection query ile tüm eval verisi yükleniyor:

var snapshot = await context.FeatureFlagEnvironments
    .AsNoTracking()
    .Where(fe => fe.FeatureFlag.Key == flagKey
                 && fe.ProjectEnvironment.Key == environmentKey
                 && fe.FeatureFlag.Project.Key == projectKey
                 && fe.FeatureFlag.Project.Organization.PublicKey == publicKey)
    .Select(fe => new FlagEvalSnapshot(
        fe.FeatureFlag.Key, fe.FeatureFlag.Type,
        fe.IsEnabled, fe.DefaultRolloutKind, fe.DefaultRolloutPercentage,
        fe.FeatureFlag.Variants.OrderBy(v => v.SortOrder).Select(...).ToList(),
        fe.VariantWeights.Select(...).ToList(),
        fe.SegmentTargetings.Where(t => t.IsEnabled).OrderByDescending(t => t.Priority)
            .Select(...).ToList()
    ))
    .FirstOrDefaultAsync(ct);
Neden tek query?
  • Round-trip sayısı 5 → 1 (eval bir hot path, latency önemli)
  • SQL tarafı bir JOIN graph'ı olarak optimize eder
  • Snapshot pattern → eval logic'i in-memory record üzerinde sync çalışır (mock'lamak, test etmek kolay)
Information disclosure trade-off: Eski 5-query "Organization bulunamadı." / "Project bulunamadı." / "Flag bulunamadı." gibi spesifik hatalar dönüyordu. Yeni versiyon hepsini "Flag bulunamadı." altında topluyor. Public endpoint için bu daha güvenli — saldırgan hangi parçanın eksik olduğunu öğrenemiyor.

Eval algoritması

if (!snapshot.EnvEnabled) → Off foreach (targeting in snapshot.Targetings): // priority desc, IsEnabled if (RulesMatch(targeting.Rules, traits, op)): return type == Multivariant ? PickVariant(snapshot, targeting.VariantWeights, userKey) : Boolean(ApplyRollout(targeting.RolloutKind, targeting.RolloutPercentage)); // hiçbir targeting eşleşmedi → env default return type == Multivariant ? PickVariant(snapshot, snapshot.EnvVariantWeights, userKey) : Boolean(ApplyRollout(snapshot.DefaultRolloutKind, snapshot.DefaultRolloutPercentage));

Bucket fonksiyonu

private static int Bucket(string flagKey, string userKey)
{
    var input = Encoding.UTF8.GetBytes($"{flagKey}:{userKey}");
    var hash = SHA256.HashData(input);
    return (int)(BitConverter.ToUInt32(hash, 0) % 100);
}
Neden SHA256, neden bu format?
  • Deterministik — aynı user her zaman aynı bucket
  • Uniform distribution — variant'lar arasında dengeli dağılım
  • "flagKey:userKey" format → bir kullanıcı farklı flag'lerde bağımsız bucket'lara düşer (cross-flag korelasyon yok, A/B testler birbirini etkilemez)
  • SHA256 cryptographic değil ama uniform; MD5 da çalışırdı ama .NET 9'da HashData API'si SHA256'da daha rahat
Server ile SDK aynı algoritmayı kullanıyor — SDK in-memory ruleset'ten eval ederken aynı SHA256 input'unu üretir. Sonuçlar birebir aynı. Aynı kullanıcı server tarafında ve SDK tarafında aynı variant'a düşer.

PickVariant detayı

private static EvaluateFlagResponseDto PickVariant(
    FlagEvalSnapshot flag,
    List<VariantWeightSnapshot> weights,
    string? userKey)
{
    if (weights.Count == 0) return Off;
    if (string.IsNullOrWhiteSpace(userKey)) return Off;   // stable bucket yoksa safe-default

    var bucket = Bucket(flag.Key, userKey);
    var weightByVariantId = weights.ToDictionary(w => w.VariantId, w => w.Weight);

    var cumulative = 0;
    foreach (var v in flag.Variants)         // SortOrder garantili sırada
    {
        if (!weightByVariantId.TryGetValue(v.Id, out var w) || w <= 0) continue;
        cumulative += w;
        if (bucket < cumulative)
            return new EvaluateFlagResponseDto(true, v.Key, v.PayloadJson);
    }
    return Off;
}
userKey yoksa Off neden? Multivariant'ta stable bucket için userKey şart. Yoksa her istek farklı variant'a düşerdi — A/B test verisi geçersiz. Safe default Off.

7. Tekrarlayan Pattern'ler

Auth check zinciri

Yetki kontrolü her write handler'ın ilk işi. Tipik desen:

var entity = await context.Variants
    .Include(v => v.FeatureFlag)
        .ThenInclude(f => f.Project)        // Organization'a kadar in
    .FirstOrDefaultAsync(...);

var isMember = await context.OrganizationMembers
    .AnyAsync(m =>
        m.OrganizationId == entity.FeatureFlag.Project.OrganizationId &&
        m.UserId == userContext.UserId, ct);

if (!isMember)
    throw new UnauthorizedAccessException("Bu organization için yetkin yok.");
Neden include ile yetki? Variant doğrudan OrganizationId taşımıyor; chain ile org'a ulaşıyoruz. Bu pattern her seviyedeki entity için aynı — flat tree'yi yukarı kaydır, OrganizationMember'a sor.

Response<T> envelope

Tüm endpoint'ler standart envelope döner:

{ "success": true, "message": null, "data": { ... }, "errors": null }

Handler'da:

return Response<Dto>.Ok(payload);           // başarı
return Response<Dto>.Fail("hata mesajı");   // beklenen iş hatası
throw new UnauthorizedAccessException(...); // 401
Throw vs Fail neden farklı?
  • Fail → "kullanıcı yanlış input verdi / iş kuralı ihlal etti" → 400 BadRequest, UI gösterir
  • throw → "should-never-happen / auth failure" → exception, üst katman handle eder

Carter endpoint pattern

Her Endpoint dosyası bir CarterModule. Carter bunu runtime'da bulup map ediyor. Boilerplate:

public class AddVariantEndpoint : CarterModule
{
    public sealed class Request { public string Key { get; set; } = default!; ... }

    public override void AddRoutes(IEndpointRouteBuilder app)
    {
        app.MapPost("/api/flag/{flagId:guid}/variants",
            async (Guid flagId, [FromBody] Request r, IMediator mediator) =>
            {
                var cmd = new AddVariantCommand(flagId, r.Key, r.Name, r.PayloadJson);
                var res = await mediator.Send(cmd);
                return res.Success ? Results.Ok(res) : Results.BadRequest(res);
            })
            .WithTags("Variant").WithName("AddVariant").RequireAuthorization();
    }
}

Endpoint sadece HTTP ↔ MediatR köprüsü; iş mantığı handler'da. Bu sayede aynı command MediatR üzerinden başka yerden de çağrılabilir (örn. background job, başka handler).

FeatureFlagType enum (Boolean=1, Multivariant=2, Config=3)

Magic number değil — int enum olarak DB'de saklanıyor. UI int gönderiyor, deserialization otomatik. FeatureFlagType.Multivariant hem .NET hem JSON.
